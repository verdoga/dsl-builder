## 1. Назначение и границы инструмента

### 1.1. Назначение

- Создавать учебные модули из технических JSON-файлов, подготовленных существующим парсером.
- Преобразовывать техническую модель парсера в модель урока по `Lesson.schema.json`.
- Находить связанные медиа, расшифровки и субтитры.
- Встраивать файлы ресурсов непосредственно в JSON уроков в Base64.
- Формировать манифест по `Manifest.schema.json`.
- Упаковывать уроки и манифест в плоский ZIP.
- Обновлять один существующий урок за одну операцию.
- Добавлять новые уроки в существующий модуль из одного файла или каталога.
- Давать пользователю возможность проверить состав и изменения до записи.

### 1.2. Поддерживаемые режимы

1. Создание нового модуля.
2. Обновление существующего модуля с загрузкой одного технического JSON.
3. Добавление уроков в существующий модуль из файла или каталога.
4. Выход.

### 1.3. Что не входит в задачу

- Разбор исходного DSL из TXT.
- Исправление исходной разметки и ошибок парсера.
- Изменение исходных технических JSON и исходных ресурсов.
- Воспроизведение медиа.
- Рендеринг текста, HTML, таблиц и интерактивных элементов.
- Разбор внутренней разметки `multifill` и извлечение из неё ответов.
- Перекодирование, сжатие с потерями или конвертация форматов медиа.
- Шифрование содержимого.
- Работа с сервером, браузером или графическим интерфейсом.
- Объединение разных курсов в один модуль.
- Удаление произвольных уроков из архива как отдельный пользовательский режим.

## 2. Источники, схемы и приоритет правил

### 2.1. Материалы проекта

| Источник | Назначение |
|---|---|
| `Contract.jsonc` | Контракт входного технического JSON: метаданные, строки, элементы, связи, диагностика |
| `Lesson.schema.json` | Структура итогового урока, типы нод и данных, роли, флаги и ограничения |
| `Manifest.schema.json` | Структура манифеста учебного модуля |
| `golden.zip` | Семь комплектов `N. parsed.json` и `N. lesson.json` для сопоставления входа и результата |
| `Unit example.ZIP` | Пример произвольной вложенности входных каталогов, повторяющихся имён файлов, секций и ресурсных каталогов |
| `Manifest flat example.json` | Пример формы манифеста без юнита |
| `Manifest unit example.json` | Пример манифеста с юнитом и секциями |
| `DSL v1.2(1).md` | Справочная семантика конструкций; не вход утилиты и не основание для повторного разбора TXT |
| Настоящее ТЗ | Итоговые требования к сборщику, включая уточнения, принятые после подготовки примеров |

### 2.2. Применение источников

- Вход для преобразования — `parsed.json` по контракту; TXT из golden используется только как справочный материал разработчика.
- Структура выходных JSON должна соответствовать приложенным схемам.
- Валидационные условия схем учитываются как правила формирования модели: обязательные поля, допустимые типы, роли, коллекции и флаги.
- При расхождении старых примеров с явно установленным правилом настоящего ТЗ применяется это ТЗ.
- Не переносить в реализацию отменённые правила только потому, что они остались в старом DSL-документе или golden.
- Не добавлять произвольные поля в выходные JSON ради удобства сборщика.
- Служебные индексы, пути, веса секций и сведения для сравнения хранить во внутренней модели.

### 2.3. Известные отличия от старых материалов

- Подстрока поиска медиа может быть любой строкой, а не только номером.
- Явный источник в кавычках означает путь; источник без кавычек означает поисковую подстроку.
- Относительные ресурсные пути вычисляются от технического JSON, а не от пути старого DSL, записанного в `document.filePath`.
- Невостребованные файлы из `resourceDirs` не встраиваются автоматически.
- Расшифровка из исходного урока становится отдельной нодой `script`; файловая расшифровка относится к медианоде.
- Смешение уроков с секциями и без секций запрещено, хотя форма манифеста технически способна его выразить.
- При новой сборке допустим синтез `order`, если он отсутствует у всех уроков группы.
- Содержимое `multifill` целиком передаётся плееру, включая специальную разметку пропусков и ответов.
- Старые эталоны не должны требовать прежней привязки `@script` к `media.data` или прежней нумерации следующих за ним нод.

## 3. Общие технические требования и ограничения

- Использовать **Go 1.25**.
- Использовать **только стандартную библиотеку Go**.
- Запретить сторонние модули, vendoring сторонних библиотек и внешние исполняемые помощники.
- Не требовать установленного Go для запуска готового `.exe`.
- Основной выпуск — консольное приложение Windows x64.
- Поддерживать запуск двойным щелчком и из уже открытой консоли.
- Не принимать параметры работы через аргументы командной строки, флаги, конфигурационные файлы или переменные окружения.
- При переданных аргументах сообщать, что работа выполняется через интерактивное меню.
- Все пользовательские сообщения выводить на русском языке.
- Корректно обрабатывать кириллицу, Unicode и пробелы в названиях и путях Windows.
- Входные технические JSON читать в UTF-8; допустимо снять один начальный UTF-8 BOM.
- Выходные JSON записывать в UTF-8 без BOM.
- Формировать JSON стандартным сериализатором; не собирать JSON конкатенацией строк.
- Использовать один общий механизм преобразования во всех трёх режимах.
- Отделить преобразование данных от диалогов, сравнения версий и записи ZIP.
- До подтверждения записи работать с внутренней моделью и планом изменений.
- Не изменять исходный архив, исходные JSON и ресурсы на этапе анализа и превью.
- Ошибки ввода, чтения, преобразования и записи обрабатывать сообщениями и меню продолжения.
- Не завершать приложение необработанной паникой при ожидаемых ошибках данных или файловой системы.
- Не использовать цвет как единственный способ обозначить ошибку или изменение.
- Не использовать полноэкранный TUI, управление курсором или автоматическую очистку истории консоли.
- Все действия должны быть доступны последовательным текстовым вводом с клавиатуры.

## 4. Термины и идентификаторы

| Термин | Значение |
|---|---|
| Технический JSON | Результат работы парсера по `Contract.jsonc` |
| Урок | Итоговый JSON по `Lesson.schema.json` |
| Модуль | Один ZIP с уроками и `manifest.json` |
| ID урока | Стабильное `document.id`, перенесённое из `document.metadata.documentId` |
| Техническое имя | Имя файла в ZIP: `l001.json` и далее; не ID урока |
| Страница | Элемент `document.pages` |
| Нода | Элемент дерева `nodes`, включая вложенные ноды |
| Группа уроков | Одна секция; при отсутствии секций — все уроки модуля |
| Вес урока | Числовое значение `order` внутри группы |
| Вес секции | Временное число для сортировки секций; в JSON не сохраняется |
| Ревизия урока | Целое `document.version` и соответствующая версия в манифесте |

## 5. Входные данные и предварительные проверки

### 5.1. Поиск входных файлов

- При создании принимать путь к каталогу.
- При обновлении принимать путь ровно к одному техническому JSON.
- При добавлении принимать путь к одному техническому JSON либо к каталогу.
- Каталоги обходить рекурсивно без искусственного ограничения глубины.
- Искать файлы с расширением `.json` без учёта регистра.
- Имена входных файлов и названия каталогов не определяют курс, юнит или секцию.
- Одинаковые имена файлов в разных каталогах допустимы.
- Каждый найденный JSON должен пройти проверку как входной технический JSON.
- Не пропускать неподходящий или повреждённый JSON молча.
- Пустой результат поиска считать ошибкой.
- Для детерминированного порядка сравнивать относительные пути от выбранного каталога.
- При совпадении пути без учёта регистра использовать исходное написание как дополнительный ключ сравнения.
- Не использовать дату файла для сортировки.
- Не обходить циклические ссылки каталогов; ошибки доступа к обязательным входным данным сообщать явно.

### 5.2. Проверка технического JSON

- Проверять корректность JSON и поддерживаемую версию `formatVersion`.
- Поддерживаемая версия входного контракта — `"1.0"`.
- Проверять наличие и типы необходимых полей контракта.
- Сохранять значение `document.metadata.documentId`; не генерировать отсутствующий ID урока.
- Отсутствующий, пустой или некорректный ID урока считать ошибкой.
- Совпадение ID разных входных уроков считать ошибкой, в том числе при различии только регистра.
- При обновлении требовать ровно одно совпадение ID с уроком в архиве.
- При добавлении запрещать совпадение ID с любым существующим уроком.
- Проверять целостность используемых `parentLine` и отсутствие циклов.
- Неизвестные поля входного контракта при поддерживаемой версии игнорировать.
- Не подставлять выдуманные значения вместо обязательных неизвестных метаданных.

### 5.3. Ошибки парсера

- Останавливать текущую операцию при любом `document.hasErrors = true`.
- Останавливать текущую операцию при наличии `diagnostics[].severity = "error"`.
- Останавливать текущую операцию при любой строке `lines[].type = "invalid"`.
- Останавливать текущую операцию при любом элементе `lines[].elements[].type = "unparsed"`.
- Наличие любого из перечисленных признаков достаточно для остановки, даже если остальные признаки с ним не согласованы.
- В сообщении указывать путь к техническому JSON, строку и колонку при наличии, признак ошибки и доступную диагностику.
- Предупреждения и рекомендации парсера не показывать.
- Ошибка одного файла запрещает запись всего результата текущей операции.
- Остановка сборки не означает аварийное закрытие утилиты.

## 6. Выходной модуль

### 6.1. Состав ZIP

- Архив содержит только JSON-файлы уроков и один `manifest.json`.
- Все записи находятся в корне ZIP.
- Подкаталоги, отдельные медиафайлы, TXT, субтитры и прочие ресурсные файлы в ZIP не создаются.
- Имена уроков соответствуют `l001.json`, `l002.json`, …, `l999.json`, `l1000.json`.
- Каждая запись урока в манифесте должна ссылаться на существующий файл ZIP.
- Каждый файл урока должен иметь ровно одну запись в манифесте.
- Дубли записей ZIP и неоднозначные ссылки запрещены.
- При чтении существующего модуля проверять его состав и согласованность манифеста с уроками.
- Не выполнять извлечение путей из ZIP за пределы рабочей области; плоский модуль не должен содержать пути каталогов.

### 6.2. Формат данных

- `formatVersion` урока: строка `"1.0"`.
- `formatVersion` манифеста: строка `"1.0"`.
- `document.version`: положительное целое число.
- `createdAt`: UTC, формат `YYYY-MM-DDTHH:MM:SSZ`.
- При создании или содержательном обновлении урока устанавливать время формирования этой версии.
- При изменениях только манифеста не изменять `createdAt` и `version` неизменённых уроков.
- При фактической записи новой версии модуля обновлять `manifest.createdAt`.
- `lineCount` переносить из `document.lineCount` технического JSON без пересчёта.
- Не использовать количество строк выходного JSON вместо `lineCount`.
- Сохранять исходные байты встроенных файлов полностью.
- Использовать стандартный Base64 с padding, без переносов внутри закодированного значения.
- Для удобства ручного просмотра записывать JSON с отступом в два пробела.
- Порядок элементов массивов сохранять согласно правилам преобразования и сортировки.

## 7. Processing ID и версии

### 7.1. ID урока и технические имена

- ID урока брать из `document.metadata.documentId`.
- Исходный регистр ID урока сохранять в уроке и манифесте.
- Для сравнения идентичности уроков использовать сравнение без учёта регистра.
- При обновлении сохранять написание ID существующего урока.
- При новой сборке назначать технические имена по порядку отсортированного списка входных путей.
- Назначение технических имён выполнять во внутренней модели до преобразования.
- При обновлении сохранять техническое имя файла урока.
- При добавлении продолжать нумерацию после максимального номера существующего `l…json`.
- Не занимать пробелы в старой нумерации.
- Изменение веса или секции не переименовывает файлы уроков.

### 7.2. Первичная генерация страниц и нод

- Префикс страниц и нод — ID урока в нижнем регистре.
- Страницы: `efx7-p001`, `efx7-p002` и далее.
- Ноды: `efx7-n001`, `efx7-n002` и далее.
- Нумерацию страниц начинать с 1 внутри урока.
- Нумерацию нод вести сквозным счётчиком внутри всего урока, без сброса на новой странице.
- Учитывать ноды любой вложенности.
- Обход для присвоения номеров: родитель, затем его дочерние ноды в порядке массива.
- Числа дополнять слева нулями до трёх цифр; после 999 использовать полное число без обрезания.
- Начальная ревизия нового урока — `1`.
- В первой ревизии суффикс версии у ID нод не добавлять.
- Новый урок, добавленный в старый модуль, также начинается с ревизии `1`.

### 7.3. Замена отдельной ноды

- Сохранять базовый номер заменяемой ноды.
- Добавлять либо заменять суффикс `-vNN`.
- `NN` обозначает новую глобальную ревизию урока, а не число изменений конкретной ноды.
- При переходе урока с версии 5 на 6 первая замена ноды `efx7-n081` даёт `efx7-n081-v06`.
- Нода `efx7-n035-v03` при той же операции становится `efx7-n035-v06`.
- Минимальная ширина версии — две цифры; ревизия 100 записывается как `-v100`.
- Неизменённые ноды сохраняют полные прежние ID.
- Замена дочерней ноды не меняет ID родителя, если собственные поля родителя не изменились.

### 7.4. Полная замена нод страницы

- ID страницы сохраняется.
- Все ноды заменяемой страницы, включая вложенные, считаются новыми.
- Всем этим нодам выдаются новые базовые номера.
- Первый номер — максимальный номер ноды во всём документе до обновления плюс 1.
- Для нескольких заменяемых страниц использовать один общий счётчик новых номеров.
- Всем новым нодам добавлять суффикс новой ревизии урока.
- Не пытаться сохранять номера отдельных старых нод заменяемой страницы.
- Ноды остальных страниц сохранять, если они не затронуты другими изменениями.
- Допускать непоследовательные номера в итоговом порядке отображения.

### 7.5. Полная замена урока

- Сохранять ID урока и техническое имя его файла.
- Увеличивать ревизию урока на единицу.
- Выдавать новые ID всем страницам и всем нодам.
- Новую нумерацию страниц начинать после максимального номера страницы старого урока.
- Новую нумерацию нод начинать после максимального номера ноды старого урока.
- Новым нодам добавлять суффикс новой ревизии.
- Не менять название и подзаголовок без подтверждения соответствующих изменений.

### 7.6. Общие правила ревизии

- За одну записанную операцию обновления увеличивать ревизию урока ровно на единицу.
- Количество заменённых нод не влияет на величину увеличения.
- Подтверждённое изменение `document.title`, `document.subtitle` или названия страницы также является изменением урока.
- Обновлять ревизию одновременно в уроке и соответствующей записи манифеста.
- Не увеличивать версии других уроков из-за изменения их положения в манифесте.
- Если содержимое урока и манифест остались прежними, не переписывать архив.
- Только изменение времени сборки не должно создавать искусственную новую ревизию.

## 8. Манифест, секции и порядок

### 8.1. Курс и юнит

- Название курса обязательно.
- Название курса запрашивается у пользователя, а не извлекается из пути.
- Название юнита необязательно.
- Пустое название юнита означает отсутствие объекта `unit`.
- При отсутствии юнита `lessons` и `sections` располагаются непосредственно в `course`.
- В превью позволять изменить название курса и задать, изменить либо убрать название юнита.

### 8.2. Формирование записи урока

| Поле манифеста | Источник |
|---|---|
| `id` | `document.id` итогового урока |
| `fileName` | Назначенное техническое имя |
| `order` | Исходный, синтезированный или явно заданный вес |
| `title` | `document.title` итогового урока |
| `subtitle` | `document.subtitle`; при отсутствии — `null` |
| `lineCount` | `document.lineCount` итогового урока |
| `createdAt` | `document.createdAt` итогового урока |
| `version` | `document.version` итогового урока |

- При новой сборке начальную секцию брать из `document.metadata.section` технического JSON.
- При изменении секции пользователем сохранять выбранное положение в манифесте.
- Секции содержат `title` и массив `lessons`.
- Пустые секции в итоговый манифест не включать.
- Пример манифеста не задаёт неизменяемый порядок технических имён.

### 8.3. Секции

- Допускать только два итоговых состояния: все уроки распределены по секциям либо все уроки находятся без секций.
- Смешанный состав запрещён.
- При новой сборке смешанные исходные значения `section` считать ошибкой.
- Имена секций сравнивать с учётом регистра, как предусмотрено контрактом.
- Новые пользовательские имена приводить к требованиям схемы: без крайних и повторных обычных пробелов, табуляции и переводов строк.
- Пустое имя секции запрещено.
- Одинаковые секции объединять, а не создавать несколько одноимённых объектов.
- Первоначально сортировать секции по алфавиту.
- Для детерминированной алфавитной сортировки сравнивать строки после приведения к нижнему регистру средствами стандартной библиотеки, затем исходное написание; системную локаль Windows не использовать.
- Для ручного изменения порядка последовательно запрашивать вес каждой секции.
- Вес секции вводить как положительное целое число.
- Сортировать секции по возрастанию веса; при равных весах — по названию.
- Вес секции хранить только во внутренней модели.
- В JSON порядок секций выражать расположением объектов в массиве `sections`.
- При создании секций в модуле без секций требовать распределить **все** уроки перед сохранением.
- До завершения распределения разрешать работу с моделью, но запрещать запись архива.

### 8.4. Вес урока

- Хранить `order` строкой с записью положительного целого числа.
- Для сортировки и проверки равенства использовать числовое значение.
- Не преобразовывать произвольные значения `order` в `float64`.
- Не ограничивать корректный исходный вес диапазоном машинного `int`.
- Сохранять ведущие нули исходного значения.
- Значения `"1"`, `"01"` и `"001"` считать одинаковыми весами.
- Проверять уникальность веса внутри одной секции.
- Для модуля без секций проверять уникальность веса среди всех его уроков.
- Одинаковые веса в разных секциях допустимы.
- Совпавшие веса уроков — **ошибка сборки**, а не предупреждение.
- Показывать в превью все конфликтующие файлы и общий вес.
- Запрещать запись до устранения совпадений.

### 8.5. Отсутствующий вес

- При **новой сборке** проверять наличие `order` отдельно в каждой группе.
- Если `order` задан у всех уроков группы — сортировать по нему.
- Если `order` отсутствует у всех уроков группы — сортировать по относительным путям и синтезировать веса `"1"`, `"2"` и далее.
- Если `order` задан только у части уроков группы — считать входные данные ошибочными.
- Синтезированный вес записывать только в манифест, не в исходный JSON.
- При **обновлении** отсутствие `order` в новом техническом JSON само по себе не удаляет уже существующий вес манифеста.
- При **обновлении и добавлении**, если у урока в итоговой модели нет веса, требовать ввести его в диалоге.
- При переносе урока в другую секцию проверять его вес в новой группе.
- Разрешать последовательно задать новые веса урокам выбранной группы.
- После изменения весов повторять сортировку, проверку конфликтов и вывод превью.

## 9. Поиск и встраивание ресурсов

### 9.1. Область поиска

- Относительные пути вычислять от каталога конкретного технического JSON.
- Не использовать текущую рабочую папку утилиты, корень всей сборки или `document.filePath` как замену этой базе.
- Значения `document.metadata.resourceDirs` образуют область автоматического поиска.
- Каждый указанный каталог обходить рекурсивно.
- Абсолютный путь Windows использовать непосредственно; относительный разрешать от каталога технического JSON.
- Повторные каталоги и пересекающиеся области поиска не должны создавать повторные кандидаты одного файла.
- Недоступный или отсутствующий явно указанный ресурсный каталог считать ошибкой.
- При отсутствии `resourceDirs` разрешать только явные пути к медиа.
- Не расширять область автопоиска произвольным обходом соседних каталогов.

### 9.2. Явный путь и подстрока

- Определять способ обращения по исходной форме элемента `source` в техническом JSON.
- Для определения кавычек использовать `elements[].raw`; значение пути брать из `elements[].value`.
- Источник в кавычках трактовать как явный путь.
- Источник без кавычек трактовать как подстроку имени файла.
- Сохранять подстроку целиком, включая ведущие нули, точки и пробелы, если она передана контрактом как одно значение.
- Сопоставлять подстроку с именем файла, а не с путём к его каталогу.
- Совпадение может находиться в любой части имени.
- Поиск выполнять без учёта регистра.
- Фильтровать кандидатов по объявленному типу `audio`, `video` или `image` и разрешённым расширениям.
- Для автопоиска требовать ровно одного кандидата.
- Ноль кандидатов — ошибка «Ресурс не найден».
- Несколько кандидатов — ошибка неоднозначности с перечислением путей.
- Не выбирать первый найденный файл автоматически.
- Явный путь не подставлять внутрь `resourceDirs`.
- Если явный путь не найден, не переходить скрытно к поиску по подстроке.
- Проверять допустимость расширения и для явного пути.

### 9.3. Расширения и MIME-типы

- Использовать фиксированную таблицу соответствий внутри приложения.
- Сравнивать расширения без учёта регистра.
- Не зависеть от MIME-настроек реестра Windows.
- Поддержка расширения означает возможность встроить байты файла; доступность декодирования определяет плеер.
- Не анализировать и не преобразовывать содержимое мультимедийных контейнеров.

### 9.4. Сопутствующие файлы

1. Найти основной аудио- или видеофайл.
2. В том же каталоге найти расшифровку `.txt` с тем же именем без последнего расширения.
3. В том же каталоге найти субтитры с тем же именем без последнего расширения.
4. Встроить основной файл, затем TXT, затем найденные субтитры.

- Для сопутствующих файлов не обходить подпапки.
- Сравнивать полное базовое имя без учёта регистра, а не искать его как подстроку.
- Расшифровка и субтитры независимы и необязательны.
- Отсутствие необязательного сопутствующего файла не является ошибкой.
- Встраивать все найденные одноимённые субтитры поддерживаемых форматов, не отбрасывая один формат ради другого.
- Порядок субтитров фиксировать: `vtt`, `srt`, `ttml`, `dfxp`, `ass`, `ssa`.
- Не подключать произвольные одноимённые файлы с другими расширениями.
- При неоднозначности имени из-за регистра сообщать об ошибке.
- При ошибке чтения найденного сопутствующего файла останавливать операцию.
- Для изображений автоматический поиск расшифровок и субтитров не выполнять.

### 9.5. Представление встроенных файлов

- Основной файл хранить в `media.data` с `type: "media"` и `role: "body"`.
- Файловую расшифровку хранить там же с `role: "script"`.
- Субтитры хранить там же с `role: "subtitles"`.
- Каждый файл представлять отдельным элементом `data`.
- В `value` сохранять `fileName` без пути, `mimeType` и `content` с Base64.
- Для этих элементов устанавливать `answers: []` и `hint: ""`.
- Если в исходном уроке также есть `script`, сохранять обе расшифровки.
- Исходный `script` преобразовывать в отдельную ноду, файловый TXT — в данные медианоды.
- Не объединять, не сравнивать и не удалять похожие расшифровки.

### 9.6. Реестр использования ресурсов

- Вести реестр файлов проверяемой области ресурсов.
- Включать в область учёта файлы из `resourceDirs`, явно подключённые файлы вне этих каталогов и их проверяемые сопутствующие файлы.
- Различать состояния «использован» и «не использован».
- Файл считать использованным после успешного включения его содержимого хотя бы в один урок текущей операции.
- Повторное использование одного пути не увеличивает число уникальных использованных файлов.
- Файлы с одинаковым именем в разных каталогах учитывать отдельно.
- Для нескольких уроков общую статистику считать по объединению путей.
- Показывать количество всех учтённых файлов, использованных и неиспользованных.
- В превью предоставлять пункт просмотра неиспользованных файлов с полными путями.
- Неиспользованный файл сам по себе не является ошибкой.
- При обновлении и добавлении явно обозначать область статистики: ресурсы обрабатываемых исходников, а не предполагаемые исходные каталоги старых уроков.

## 10. Компактный алгоритм преобразования технического JSON

### 10.1. Общая последовательность

1. Прочитать и проверить технический JSON.
2. Извлечь метаданные урока, сведения для манифеста и ресурсные каталоги.
3. Построить индекс строк по `line` и связей по `parentLine`.
4. Зарегистрировать определения фрагментов, если они присутствуют.
5. Обойти строки в исходном порядке.
6. Сформировать страницы, задания, этапы и ветви с сохранением семантической вложенности.
7. Сформировать собственные данные каждой ноды.
8. Привязать ответы и подсказки к соответствующим элементам.
9. Подключить медиа и сопутствующие файлы.
10. Сформировать допустимые флаги.
11. Назначить первичные ID; в режиме обновления использовать полученную модель как кандидат для сравнения.
12. Проверить сформированный урок по ограничениям выходного контракта.
13. Передать урок и извлечённые метаданные общему механизму сборки или обновления.

### 10.2. Общие правила преобразования

- Работать с `lines` и `elements` технического JSON, не запускать повторный DSL-парсер.
- Использовать семантические `value` элементов.
- Использовать `raw` и диапазоны только там, где нужно сохранить переданную парсером структурированную запись или отличить кавычки источника.
- Не снимать экранирование повторно со значений, уже обработанных парсером.
- Сохранять исходный порядок содержательных элементов.
- Не переносить в урок `processing`, `diagnostics`, `raw`, `eol`, `parentLine`, диапазоны колонок и прочие технические сведения.
- Не создавать ноды для метатегов, редакторских комментариев, границ блоков и `endtask`.
- Не использовать `nestingLevel` как единственный способ построить дерево.
- Учитывать текущие семантические контейнеры даже там, где `parentLine` указывает на общий контейнер.

### 10.3. Метаданные и страницы

| Вход | Выход |
|---|---|
| `document.metadata.documentId` | `document.id` |
| `document.metadata.title` | `document.title` |
| `document.metadata.subtitle` | `document.subtitle` |
| `document.lineCount` | `document.lineCount` |
| Заголовок уровня 3 | Новая страница с соответствующим `title` |
| `newpage` | Граница новой страницы без собственного названия |
| Отсутствие границ страниц | Одна страница |

- Заголовки уровней 1 и 2 не дублировать как самостоятельные ноды.
- Материал до первой явной границы страницы сохранять на начальной странице.
- Не создавать фиктивную пустую начальную страницу перед первым заголовком уровня 3.
- При отсутствии собственного заголовка записывать `page.title: null`.
- Не подставлять название документа вместо отсутствующего названия страницы.
- `header` создаёт ноду `heading` и не создаёт страницу.

### 10.4. Границы и вложенность task

1. При элементе `tag` со значением `task` открыть контекст задания.
2. Использовать номер исходной строки задания как ключ его контекста.
3. По цепочкам `parentLine` определять принадлежность строк заданию и вложенным блокам.
4. Добавлять созданные дочерние ноды в `task.nodes`.
5. При `step` открыть внутренний этап внутри этого задания.
6. Последующее содержимое этапа размещать в `step.nodes` до следующего этапа или завершения задания.
7. Закрыть задание при `endtask`, следующем задании того же уровня, границе страницы, выходе из содержащей его ветви/контейнера или конце документа.

- Закрытие внутреннего блока не завершает задание.
- Отдельный `instr` внутри задания остаётся дочерней нодой задания либо его активного этапа.
- Внешние ноды после `endtask` не помещать в предыдущее задание.
- В `variants` учитывать активную ветвь `variant`.
- Повторяющийся исходный ID задания в разных ветвях не считать одним объектом.
- Для исходного `task` его отображаемый идентификатор сохранять в данных с ролью `title`, как в golden.
- У `task` выставлять `speaking` по наличию соответствующего признака.
- У `task` выставлять `stepped` по наличию внутренних этапов.
- Структура `task → step → nodes` обязательна, даже если строки этапа в техническом JSON имеют `parentLine` самого задания.

| `variant` | `variant` |

| `key` | `answerKey` |
| `wordlist` | `wordList` |

| Обычный самостоятельный учебный текст | `text` |

### 10.6. Собственные данные ноды

- Каждая нода содержит `id`, `type`, `flags`, `data`, `nodes`.
- При отсутствии дочерних нод записывать `nodes: []`.
- При отсутствии собственных данных записывать `data: []`.
- Для допустимых типов без флагов записывать `flags: {}`.
- Название текстового блока помещать в элемент `data` с ролью `title`.
- Основное текстовое содержимое помещать в элемент с ролью `body`.
- Каждый элемент данных содержит `type`, `value`, `answers` и `hint`.
- Допустимые типы данных: `text` — строка; `media` — встроенный файл; `collection` — массив элементов данных.
- Допустимые роли: `title`, `body`, `instruction`, `before`, `after`, `items`, `item`, `options`, `option`, `positions`, `position`, `hint`, `script`, `subtitles`.
- Для непосредственных элементов `Node.data` роль обязательна.
- При отсутствии ответов записывать `answers: []`.
- При отсутствии подсказки записывать `hint: ""`.
- Не путать поле `hint` элемента данных с отдельной нодой `hint`.

### 10.7. Текст, таблицы и multifill

- Содержимое `text`, `table` и `multifill` сохранять одной многострочной строкой в `body.value`.
- Строки соединять символом `\n`.
- Таблицы не разбивать на строки объектов и ячейки.
- HTML и другую внутреннюю разметку не рендерить и не преобразовывать.
- Список слов не разбивать на отдельные элементы по точкам с запятой.
- В `multifill` сохранять пустые строки.
- В остальных текстовых блоках пустые исходные строки отбрасывать.
- Сохранять явные непустые элементы разметки визуального разрыва.
- В `multifill` сохранять специальные записи пропусков и ответов целиком, включая `_____{ANSWER}`.
- Не переносить ответы из внутренней разметки `multifill` в `body.answers`.
- Обработку пропусков и проверку ответов `multifill` оставлять плееру.
- Для `multifill` не вычислять `checkable` по содержимому; оставлять допустимый по схеме `flags: {}`.
- Отсутствие этого необязательного флага у `multifill` не означает запрета проверки плеером.
- Пустой `multifill` представлять элементом `body` со значением `""`.
- У `example` с содержательным разделителем формировать роли `before` и `after`.
- У `example` без разделителя сохранять содержимое как `body`.

### 10.8. Инструкции

- Самостоятельный `instr` преобразовывать в отдельную ноду `instruction`.
- Инструкцию из объявления `multifill`, `ordering` или `matching` преобразовывать в отдельную ноду `instruction` (`NodeInstruction`).
- Такую ноду размещать непосредственно перед соответствующим интерактивным элементом на том же уровне.
- В `data` нод `multifill`, `ordering` и `matching` роль `instruction` запрещена.
- Только инструкцию из объявления `choice` или `multichoice` сохранять внутри соответствующей ноды как `type: "text"`, `role: "instruction"`.
- Для этих двух типов разрешать не более одного такого элемента.
- Отдельный исходный `instr` и инструкция в объявлении элемента сохраняются оба.
- Не удалять и не объединять совпадающие по тексту инструкции автоматически.

### 10.9. Ответы, подсказки и коллекции

- У `question` хранить формулировку в `body`.
- Связанные с вопросом ответы помещать в `answers` его элемента `body`.
- Связанную подсказку помещать в `hint` этого элемента.
- У `singleChoice` и `multipleChoice` формировать ровно одну коллекцию `options`.
- Каждый вариант этой коллекции имеет `type: "text"` и `role: "option"`.
- У правильного варианта `answers` содержит его собственное текстовое значение.
- У неправильного варианта `answers` пуст.
- У `matching` формировать ровно одну коллекцию `items` и ровно одну `options`.
- У `ordering` формировать ровно одну коллекцию `items` и, при наличии явных позиций, не более одной `positions`.
- Элементы `items` имеют роль `item`.
- Элементы `positions` имеют роль `position`.
- Все `item`, `option` и `position` имеют `type: "text"`.
- Коллекции `options` и `positions` содержат не менее двух элементов.
- Коллекция `items` у `matching` содержит не менее одного элемента, у `ordering` — не менее двух.
- Коллекции `options` и `positions` не вкладываются в другие коллекции.
- Ответы элементов `matching` и `ordering` относятся к конкретным `item`.
- Отсутствие `positions` у `ordering` означает стандартные позиции `1…N`.
- У коллекций без собственных ответов устанавливать `answers: []`.
- Общую подсказку группы правильных вариантов копировать в `hint` каждого соответствующего варианта.
- Подсказку внутри инструкции связывать с её текстовыми данными, как показано в golden.
- Самостоятельную подсказку вне такой связи сохранять отдельной нодой.
- Для интерактивных типов, кроме особого случая `multifill`, вычислять `checkable` по наличию корректных данных проверки.
- У `task` разрешены только флаги `speaking` и `stepped`; у интерактивных нод — только `checkable`; у остальных типов `flags` должен быть пустым.
- Неприменимый флаг запрещён даже со значением `false`.
- Неполную либо противоречивую конфигурацию ответов не исправлять автоматически.
- Не разрешать роли `item`, `option` и `position` непосредственно в `Node.data` или в чужих коллекциях.

### 10.10. Фрагменты

1. Собрать определения `fragment` по всему текущему техническому документу.
2. При `include` найти единственное соответствующее определение.
3. Создать отдельный экземпляр его содержимого в месте включения.
4. Назначить созданным нодам собственные ID в общем порядке обхода.

- Определение фрагмента само по себе не создаёт отображаемую ноду.
- Несколько включений создают независимые экземпляры.
- Отсутствующее или неоднозначное определение считать ошибкой.
- Не переносить `fragment` и `include` как неизвестные типы в выходную модель.

## 11. Алгоритм создания нового модуля

1. Показать главное меню и получить выбор режима.
2. Запросить каталог входных технических JSON.
3. Запросить обязательное название курса.
4. Запросить необязательное название юнита.
5. Найти JSON рекурсивно, отсортировать пути и назначить технические имена.
6. Проверить все входные документы и их ID.
7. Проверить согласованность секций и правил наличия `order`.
8. Преобразовать уроки общим механизмом.
9. Подключить ресурсы и сформировать реестр их использования.
10. Сформировать манифест во внутренней модели.
11. Проверить уроки, манифест, веса и согласованность итогового состава.
12. Показать превью модуля.
13. Обработать выбранные пользователем изменения названий, порядка секций или весов.
14. После каждого изменения повторить проверки и показать актуальное превью.
15. При выборе создания запросить отдельно каталог назначения и имя архива.
16. Показать полный путь результата и окончательное подтверждение записи.
17. При существующем целевом файле явно запросить подтверждение перезаписи.
18. Записать и проверить ZIP.
19. Сообщить полный путь результата и предложить возврат в главное меню.

## 12. Сравнение и обновление урока

### 12.1. Что сравнивается

- Сравнивать разобранные структуры модели, а не текст JSON.
- Не считать различиями отступы, порядок ключей объектов и оформление сериализации.
- Для собственных изменений ноды сравнивать `type`, `flags` и `data`.
- Дочерние ноды сравнивать отдельно.
- Вложенные элементы `data` сравнивать рекурсивно с сохранением порядка массивов.
- Сравнивать встроенные ресурсы по имени, MIME-типу и содержимому.
- Не использовать совпадение первично сгенерированных ID как доказательство идентичности нод.
- Исключать генерируемые ID, новую дату и новую ревизию из определения содержательных отличий.
- Не сопоставлять по одному номеру ID старые ноды с заново сгенерированными нодами после структурных изменений.
- Не считать одно изменение `lineCount` из-за технического редактирования основанием для искусственной пересборки.
- При фактическом изменении урока переносить актуальный `lineCount` из нового входа.

### 12.2. Уровни замены

| Ситуация | Действие |
|---|---|
| Собственные поля ноды изменились при сохранённой структуре | Заменить эту ноду, сохранить базовый номер, изменить суффикс |
| Две ноды одинаковой структуры поменялись местами | Допустимо обработать как две замены на соответствующих позициях |
| Изменилось число или вложенность нод, возник структурный сдвиг внутри страницы | Заменить все ноды затронутой страницы с новыми номерами |
| Изменился только `page.title` | Подтверждение изменения названия; ID страницы сохраняется |
| Добавлены, удалены или переставлены страницы | Полностью заменить урок с сохранением ID урока |
| Изменились только размещение и веса в манифесте | Изменить манифест; сохранить содержимое и ревизии неизменённых уроков |
| Содержательных изменений нет | Не записывать архив |

### 12.3. Правила определения уровня замены

- При сохранённой структуре обходить ноды последовательно по соответствующим позициям.
- После обнаружения изменения продолжать сравнение остальных нод.
- Не считать каждое последующее отличие автоматическим основанием для полной замены урока.
- Изменение количества дочерних нод или их вложенности считать структурным изменением страницы.
- Для замены страницы не применять произвольные процентные пороги «больших изменений».
- Для страниц учитывать их количество, последовательность и содержимое.
- Переименование страницы само по себе не означает её перестановки.
- Перестановку страниц устанавливать по содержимому, а не по совпадению вновь выданных `p…`.
- Если состав страниц изменён и безопасное соответствие старых и новых страниц установить нельзя, планировать полную замену урока и объяснять причину в превью.
- Не обещать восстановление истории редактирования по двум снимкам без устойчивых исходных ID.
- В неоднозначном случае не переносить старые ID между различными страницами догадкой.
- Все принятые решения об уровне замены показывать до записи.

### 12.4. Алгоритм обновления

1. Запросить путь к существующему ZIP.
2. Проверить ZIP, манифест и согласованность уроков.
3. Запросить путь к одному техническому JSON.
4. Проверить входной JSON.
5. Найти урок по ID; при отсутствии или неоднозначности остановить операцию.
6. Преобразовать новый вход общим механизмом, включая ресурсы.
7. Сравнить метаданные, страницы и ноды.
8. Для каждого изменения `document.title`, `document.subtitle` и `page.title` показать старое и новое значения и получить отдельное подтверждение.
9. При отказе от изменения отдельного поля оставить старое значение.
10. Сформировать план точечных замен, замен страниц либо полной замены урока.
11. Рассчитать новую ревизию и итоговые ID для принятого плана.
12. Предложить разрешённые изменения секций и весов манифеста.
13. Проверить итоговую модель всего модуля.
14. Показать подробное превью, включая изменения манифеста.
15. Если изменений не осталось, сообщить об этом и не переписывать архив.
16. Запросить `1. Да / 2. Нет` на запись.
17. При согласии безопасно записать обновлённый архив по исходному пути.
18. Сообщить результат и вернуть управление в меню.

### 12.5. Редактирование структуры манифеста при обновлении

- Разрешать перенести урок в одну из существующих секций.
- Разрешать создать секцию по введённому имени.
- Разрешать менять веса уроков выбранной группы последовательными вопросами.
- Разрешать менять порядок секций через временные веса.
- При первоначальном введении секций распределять все существующие уроки.
- Эти операции относятся к манифесту и не требуют повторного преобразования остальных уроков.
- Уже существующее размещение урока считать исходным состоянием; различия метаданных нового входа показывать как предлагаемые изменения.
- Не переносить урок и не менять его вес без подтверждения.
- Проверять ограничения по всему итоговому модулю, включая нетронутые уроки.

## 13. Алгоритм добавления уроков в существующий модуль

1. Запросить путь к существующему ZIP.
2. Проверить архив и прочитать его модель.
3. Запросить путь к техническому JSON или каталогу.
4. Для каталога рекурсивно найти технические JSON.
5. Упорядочить новые входы по относительным путям.
6. Проверить входы и уникальность их ID между собой и относительно архива.
7. При совпадении ID объяснить, что для этого урока нужен режим обновления.
8. Преобразовать новые уроки общим механизмом.
9. Назначить им технические имена после максимального номера существующего файла.
10. Добавить записи в модель манифеста.
11. Согласовать секции итогового состава; при введении секций распределить все уроки.
12. Запросить отсутствующие веса и устранить совпадения.
13. Показать превью добавляемых уроков, итоговой структуры, ресурсов и изменений манифеста.
14. Запросить окончательное подтверждение записи.
15. Перезаписать модуль с сохранением всех неизменённых уроков.
16. Показать результат операции.

- Существующие уроки не преобразовывать повторно.
- Их ID, версии, даты и технические имена сохранять.
- Существующие файлы уроков переносить без изменения их содержимого.
- Новые уроки создаются с ревизией `1`.
- Не подменять добавление скрытым обновлением совпавшего ID.
- Не допускать частичного добавления набора при ошибке одного из новых файлов.

## 14. Интерфейс и подтверждения

### 14.1. Общие правила ввода

- Выводить название `DSL-Builder` и версию `v1.0.0`.
- Версия может измениться при пересборке. Она не должна быть захардкожена.
- Каждый пункт меню размещать на отдельной строке.
- Каждый выбор обозначать числом.
- Выбор подтверждается Enter.
- Не использовать ответы `yes/no`, `y/n`, `да/нет` в свободной текстовой форме.
- Для подтверждений использовать `1. Да` и `2. Нет`.
- Свободный ввод разрешать для путей, названий и числовых весов.
- Пустой ввод разрешать только там, где это явно указано.
- Некорректный выбор объяснять и повторять тот же вопрос.
- При вставке Windows-пути принимать внешнюю пару кавычек как оформление ввода.
- Кавычки интерактивного пути не смешивать с правилом кавычек `source` внутри технического JSON.
- При отмене не применять неподтверждённые изменения.
- Потерю ввода или завершение потока обрабатывать как отмену незаписанной операции.

### 14.2. Уровни подтверждения

- Переход по меню подтверждается вводом номера и Enter.
- Изменение пользовательских метаданных предварительно показывается в виде «было → станет».
- Каждую замену поля вне ноды подтверждать отдельно.
- Замены нод подтверждаются общим подробным превью операции.
- Запись или перезапись архива требует окончательного подтверждения.
- Одно подтверждение записи относится ко всей показанной операции, включая её служебную временную запись.
- Не запрашивать подтверждение на каждый внутренний байтовый блок или каждый технический вызов записи.
- После изменения плана ранее показанное подтверждение не использовать: вывести актуальное превью.

### 14.3. Превью создания и добавления

- Показывать курс.
- Показывать юнит только при его наличии.
- Группировать уроки по секциям, если секции есть.
- Показывать секции в их итоговом порядке с номерами отображения.
- Каждый урок выводить одной компактной строкой.
- В строке указывать техническое имя, название, необязательный подзаголовок, вес, `lineCount`, число страниц и число всех нод.
- Количество нод считать рекурсивно.
- При новой сборке не выводить версию каждого урока: она равна 1.
- Показывать итоговое количество уроков, страниц и нод.
- Показывать счётчики ресурсов.
- Отдельно выводить конфликты `order`.
- В превью добавления явно помечать новые уроки.
- Не выводить содержимое нод и Base64.

### 14.4. Действия из превью

- Записать результат, если нет блокирующих ошибок.
- Изменить порядок секций, если они есть.
- Изменить веса уроков выбранной группы.
- Изменить название курса.
- Задать, изменить или убрать название юнита.
- Просмотреть неиспользованные ресурсы.
- В режимах обновления и добавления — управлять распределением по секциям и создавать секции.
- Отменить операцию и вернуться в главное меню.
- Показывать только применимые действия.
- После изменения набора действий выводить актуальную нумерацию меню.

### 14.5. Превью обновления

- Указать путь к архиву.
- Указать техническое имя и ID изменяемого урока.
- Показать название и подзаголовок для идентификации.
- Показать переход версии урока.
- Перечислить подтверждённые изменения метаданных.
- Для отдельной ноды указать страницу, полный старый ID и полный новый ID.
- Для замены нод страницы указать её ID, название и конкретную структурную причину.
- При замене страницы перечислить старые и новые ID отдельно; не изображать несуществующее попарное соответствие.
- При полной замене урока явно назвать этот уровень операции.
- Показать изменения манифеста с полями, старыми и новыми значениями.
- До записи использовать формулировки «будет заменено», «будет записано».
- Не печатать целиком JSON ноды.
- Не сокращать непоследовательные ID до вводящего в заблуждение сплошного диапазона.

## 15. Ошибки, диагностика и сохранность данных

### 15.1. Блокирующие ошибки

- Некорректный путь или отсутствие обязательного файла.
- Ошибка чтения или записи.
- Некорректный технический JSON.
- Неподдерживаемая версия контракта.
- Признаки ошибки парсера.
- Отсутствующий или дублирующийся ID урока.
- Несогласованность манифеста и ZIP.
- Смешение уроков с секциями и без секций.
- Частичное наличие исходного `order` внутри группы при новой сборке.
- Отсутствующий обязательный вес в итоговой модели обновления или добавления.
- Совпадение весов уроков в одной группе.
- Отсутствующий или неоднозначный обязательный медиаресурс.
- Недопустимое расширение ресурса.
- Нарушение ограничений выходной модели.
- Незавершённое распределение уроков по секциям.

### 15.2. Формат диагностики

- Указывать понятную причину.
- Указывать конкретный путь или техническое имя урока.
- При наличии указывать ID урока, страницу, строку и колонку.
- Для конфликтов показывать все участвующие файлы.
- Для неоднозначного ресурса показывать все найденные пути.
- Для неверного веса показывать исходное введённое значение.
- Не заменять сообщение о проблеме одним стеком вызовов.
- Не называть неиспользованные ресурсы ошибкой отсутствующего медиа.

### 15.3. Возврат после ошибки

- Для неверного ввода разрешать повторить ввод.
- Для ошибок исходных данных разрешать повторить анализ после исправления файлов.
- Для исправляемых конфликтов манифеста разрешать вернуться к редактированию весов или секций.
- Всегда предоставлять возврат в главное меню.
- Предоставлять выход из программы через числовой пункт.
- Не записывать частично готовый модуль как успешный результат.

### 15.4. Запись архива

1. Получить окончательное подтверждение пользователя.
2. Создать временный ZIP рядом с целевым файлом.
3. Записать все итоговые файлы и манифест.
4. Завершить запись и закрыть архив.
5. Проверить возможность чтения ZIP и согласованность его состава.
6. Заменить целевой файл только после успешной подготовки результата.
7. При сбое сохранить исходный архив либо восстановить его, не объявляя успех.
8. Удалить ненужные временные файлы после успешного завершения.

- Не уничтожать исходный архив в начале операции.
- Не сообщать об успехе до завершения записи и замены файла.
- При невозможности безопасно закончить операцию сообщать путь сохранённого исходника или временного результата.
- Для нового архива отдельно запрашивать каталог и имя файла.
- Добавлять `.zip`, если пользователь ввёл имя без расширения.
- Не удваивать уже указанное расширение `.zip`.
- Запрещать разделители каталогов в отдельно вводимом имени файла.
- Проверять допустимость имени в Windows.
- При перезаписи показывать полный путь существующего файла.

## 18. Пользовательские сценарии

### 18.1. Новый модуль без секций и исходных весов

1. Пользователь выбирает создание.
2. Указывает каталог, название курса и оставляет юнит пустым.
3. Утилита находит файлы на любой глубине.
4. Проверяет, что у всех отсутствует секция и у всей группы отсутствует `order`.
5. Сортирует по относительным путям и синтезирует веса.
6. Преобразует уроки и встраивает ресурсы.
7. Показывает плоское превью и статистику ресурсов.
8. Пользователь просматривает список неиспользованных файлов.
9. Указывает каталог назначения и имя ZIP.
10. Подтверждает запись.
11. Получает плоский архив с уроками и манифестом без `unit`.

### 18.2. Исправление текста в одной ноде

1. Пользователь выбирает обновление.
2. Указывает архив и один технический JSON с прежним ID урока.
3. Утилита преобразует вход и находит отличие собственных данных одной ноды.
4. Сохраняет её базовый номер и задаёт суффикс новой ревизии урока.
5. Сохраняет ID остальных нод и родителя.
6. Показывает заменяемый ID, новый ID и изменения манифеста.
7. Пользователь подтверждает запись.
8. Утилита сохраняет урок с увеличенной ревизией и обновлённый манифест.

### 18.3. Изменение структуры одной страницы

1. Пользователь предоставляет обновлённый технический JSON.
2. Утилита обнаруживает изменение числа или вложенности нод страницы.
3. Планирует замену всех нод этой страницы.
4. Сохраняет ID страницы.
5. Назначает новые номера после максимального номера ноды старого документа.
6. Добавляет всем новым нодам суффикс новой ревизии.
7. Показывает причину, старые и новые ID.
8. После подтверждения записывает результат.

### 18.4. Изменение состава страниц

1. Пользователь предоставляет урок с добавленной, удалённой или переставленной страницей.
2. Утилита определяет необходимость полной замены урока.
3. Сохраняет ID урока и имя файла в ZIP.
4. Выдаёт новые ID страницам и нодам.
5. Показывает новый состав и переход версии.
6. После подтверждения заменяет урок и актуализирует манифест.

### 18.5. Добавление уроков и введение секций

1. Пользователь выбирает добавление и указывает существующий модуль без секций.
2. Указывает каталог новых технических JSON.
3. Утилита проверяет уникальность ID и преобразует новые уроки.
4. Пользователь создаёт секции.
5. Распределяет по ним все старые и новые уроки.
6. Задаёт отсутствующие веса.
7. Исправляет совпавшие веса, если они возникли.
8. Проверяет превью всего итогового состава.
9. Подтверждает запись.
10. Утилита сохраняет прежние файлы уроков, добавляет новые и меняет манифест.

### 18.6. Отказ от изменения названия

1. Утилита обнаруживает новое название урока.
2. Показывает прежнее и новое значение.
3. Пользователь выбирает отказ.
4. Утилита оставляет прежнее название в модели урока и манифесте.
5. Продолжает подготовку других изменений.
6. Если после отказов изменений не осталось, сообщает об этом без записи архива.

## 19. Проверки реализации и критерии приёмки

### 19.1. Проверка соответствия схемам

- Проверки выходной модели реализовать средствами стандартной библиотеки.
- Универсальный интерпретатор всего JSON Schema Draft 2020-12 не требуется.
- Требуется реализовать ограничения используемых фиксированных схем для поддерживаемых форматов.
- Не заменять проверку семантики успешной сериализацией JSON.
- Проверять допустимые типы, обязательные поля, роли коллекций, флаги, число обязательных коллекций и размещение инструкций.
- Проверять связи манифеста с файлами и метаданными уроков отдельно от схемы.
- Проверять уникальность ID и числовых весов отдельно: `uniqueItems` объектов её не обеспечивает.
- При изменении схемы повторно пересматривать правила преобразования и проверки.

### 19.2. Набор проверок

- Преобразование всех актуализированных golden-пар.
- Вложенность `task`, `step` и ветвей `variants`.
- Явное завершение задания через `endtask`.
- Завершение задания границей страницы или содержащего контейнера.
- Сохранение `multifill` целиком, включая пустые строки и внутреннюю разметку.
- Сохранение таблиц и текста без рендеринга.
- Раздельное размещение инструкций согласно типу интерактивной ноды.
- Обязательные роли `item`, `option` и `position`.
- Привязка ответов и подсказок.
- Независимые экземпляры включённых фрагментов.
- Нумерация страниц и вложенных нод, включая значения больше 999.
- Поиск по любой подстроке и отличие её от явного пути.
- Разрешение относительных путей от технического JSON.
- Неоднозначный и отсутствующий ресурс.
- Поиск сопутствующих файлов только в каталоге основного медиа.
- Сохранение обеих расшифровок.
- Декодирование Base64 обратно в исходные байты.
- Реестр использованных и неиспользованных ресурсов без двойного счёта.
- Синтез весов, частичное отсутствие весов и числовые дубли.
- Изменение секций и весов по всему итоговому составу.
- Замена одной ноды без изменения ID родителя.
- Замена всех нод одной страницы.
- Полная замена урока при изменении страниц.
- Синхронизация суффиксов изменённых нод с ревизией урока.
- Отказ от отдельных изменений метаданных.
- Отсутствие записи при отсутствии изменений.
- Добавление файла и каталога; отказ при существующем ID.
- Сохранение неизменённых уроков при обновлении и добавлении.
- Отказ от записи, ошибка записи и сохранность исходного архива.
- Работа с кириллицей, пробелами и длинными допустимыми путями Windows.
- Полный проход меню только цифровыми выборами.

### 19.3. Работа с golden

- Использовать технические JSON как непосредственный тестовый вход преобразователя.
- Актуализировать ожидаемые JSON под итоговые правила этого ТЗ.
- Сравнивать модели, не требуя совпадения пробелов и порядка ключей.
- Для `createdAt` использовать фиксируемое в тесте время.
- Ресурсы создавать как небольшие тестовые файлы; не принимать `AA==` за реальный медиафайл.
- Учесть отдельную ноду для исходного `script` и вызванный этим сдвиг первичных ID.
- Учесть передачу `multifill` плееру без вычисления его `checkable`.
- Добавить отсутствующие примеры, если правило не покрывается приложенным набором.
